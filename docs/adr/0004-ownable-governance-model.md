# 0004. 権限モデルはOwnableパターンを採用し、アップグレード可能コントラクトは採用しない

- 日付: 2026-09-21
- ステータス: Accepted

## コンテキスト

チャットルームURL・理念/目標メッセージの追加・削除権限について、初期バージョンではデプロイ者(Owner)が保持し、将来的にはメンバー投票で選出されたCouncilへ委譲したいという要件がある。権限移譲の実現方法として、(a) `Ownable.transferOwnership()` でOwnerアドレス自体を将来のCouncil管理アドレス(マルチシグ等)に付け替える方式と、(b) コントラクト自体をアップグレード可能なプロキシパターンにして将来ロジックを差し替える方式が考えられる。

## 決定

- 権限モデルには標準的な `Ownable` パターン(例: OpenZeppelin `Ownable`)を採用する。
- 将来Councilへ権限を移譲する際は、`transferOwnership()` によってOwnerアドレスをCouncil運用のマルチシグウォレット等に付け替えることで対応する。
- **アップグレード可能コントラクト(プロキシパターン)は採用しない。**
- メンバーの削除権限は、本人(自己脱退)とOwnerのみに限定する。メンバー同士の相互削除は不可とする。

## 代替案

- **アップグレード可能プロキシ(UUPS/Transparent Proxy等)**: ロジック自体を後から差し替えられる柔軟性があるが、プロキシ特有の複雑性・監査コスト・アップグレード権限の乗っ取りリスクが増す。ユーザーが明確にアップグレード可能コントラクトを望まないため不採用。
- **メンバー同士の相互削除を許可する**: メンバー間のトラブルによる濫用リスクがあるため不採用。削除権限は本人とOwner(将来はCouncil)に限定する。

## 影響

- コントラクトは非アップグレード型のシンプルな実装となり、監査・検証がしやすい。
- Council移行時は新しいコントラクトへの移行(再デプロイ)ではなく、既存コントラクトのOwnerアドレス付け替えのみで対応できる。
- Council選挙ロジック自体(投票コントラクト)は将来フェーズで別途設計する。
