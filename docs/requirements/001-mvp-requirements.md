# 001. 気候変動国際協調プラットフォーム 要件定義書(初期バージョン)

- 作成日: 2026-09-21
- 更新日: 2026-09-21
- ステータス: Draft(4.6ガバナンストークンについて8章のOpen Questions 3件が確認待ち)
- 対象範囲: 初期バージョン(MVP)

## 1. 背景・目的

気候変動に関心を持つ人々が、
1. 自ら対策を行い、
2. 自国政府に対策を促し、あるいは対策を行うリーダーを選ぼうとする

ことを目的とした、国際協調のための枠組み(コミュニティ/組織)をWeb3上に構築する。特定の国・組織に依存しない、ブロックチェーン上の中立的なメンバーシップとガバナンスの基盤を提供する。

## 2. スコープ

### 2.1 対象とする機能(初期バージョン)

1. メンバー管理(既存メンバー1名が単独で追加可能、追加者の記録)
2. アドレスのみによる本人識別(個人情報を保持しない)
3. チャットルームURLの登録・管理(複数登録可能、初期はOwner権限)
4. 会の理念・当面の目標のメッセージ登録・管理(複数登録可能、初期はOwner権限)
5. ガバナンストークン(ERC20)の発行(4.6参照。**要件漏れとして追加**、2026-09-21)

### 2.2 対象外(初期バージョン)

- ステーブルコイン(USDC等)の対応全般(将来検討事項とし、初期バージョンでは考慮しない。下記4.3参照)
- メンバー投票によるCouncil選出・Council自体の権限委譲ロジック(将来対応。権限移譲の受け皿は`Ownable.transferOwnership()`で対応、詳細は7.3参照)
- KYCや個人情報の管理全般
- Mainnetにおける複数チェーンへの同時運用(1チェーンを選択して運用する。7.2参照)
- **DAOとしての機能そのもの**(トークンによる投票、提案、Treasury管理等)。今回追加するのは将来DAO化を検討する際の準備としてのガバナンストークン(ERC20)発行のみであり、そのトークンを使った意思決定の仕組みは実装しない(4.6参照)。

## 3. 技術要件

### 3.1 コントラクト

- 言語: Solidity
- 開発・テスト・デプロイツール: Foundry
- Polkadot Hubへは **REVM実行バックエンド**(標準EVMバイトコードをそのまま実行)を使用し、素のFoundryでデプロイする。PolkaVM(PVM)実行バックエンドおよび専用コンパイラ`resolc`は、現時点で公式ドキュメント上も "early-stage development and may be unstable or incomplete" とされているため採用しない(詳細は [ADR-0003](../adr/0003-use-foundry-with-revm-backend-for-polkadot-hub.md))。

### 3.2 フロントエンド

- フレームワーク: Next.js
- デプロイ先: Vercel

### 3.3 デプロイ対象チェーン

| チェーン | Mainnet | Testnet |
|---|---|---|
| Ethereum | 候補 | Sepolia |
| Polkadot Hub | 候補 | Polkadot Hub Testnet |

- **開発・検証段階**では両テストネット(Sepolia / Polkadot Hub Testnet)にデプロイし、動作確認を行う。
- **本番運用(Mainnet)では、Ethereum MainnetとPolkadot Hub Mainnetのどちらか一方のみを選び、単一チェーンで運用する。** 同時運用によるメンバーシップ不整合の問題(7.2参照)はこの方針により発生しない。どちらを選ぶかは要件定義のスコープ外とし、デプロイ時の運用判断とする。
- コントラクト自体はどちらのチェーンにもデプロイ可能な、チェーンに依存しない実装とする。

## 4. 機能要件

### 4.1 メンバー管理

- コントラクトデプロイ時に、Ownerを最初のメンバー(メンバー#1)として自動登録する(7.1)。
- 既存メンバーは、他のメンバーの承認や合議を必要とせず、**単独で**新規メンバーを追加できる(1名の既存メンバーの操作のみで完了する)。
- 「誰が追加したことでメンバーになったか」をオンチェーンで後から確認できるようにする(追加者アドレスを記録)。
- メンバーの削除権限は、**本人(自己脱退)** と **Owner** のみが持つ(7.6)。メンバー同士がお互いを削除することはできない。

### 4.2 アイデンティティ / プライバシー

- 氏名・メールアドレス等の個人情報は一切保持しない。
- ブロックチェーンアドレスのみを個人の唯一の識別子とする。

### 4.3 ステーブルコイン対応

- 初期バージョンでは対応しない。設計上の特別な配慮(将来の拡張余地を残すための抽象化など)も不要と判断した(7.7参照)。将来必要になった時点で改めて要件定義を行う。

### 4.4 チャットルームURLの登録

- メンバーが議論するためのチャットルームのURLを登録できる機能。
- **複数のURLを登録・保持できる**(1件のみではなくリストとして管理する)。
- 権限: 初期バージョンはデプロイ者(Owner)のみが追加・削除できる。
- 将来: メンバーの投票で選出されたCouncilに追加・削除権限を移譲する。

### 4.5 理念・目標メッセージの登録

- 「この会が大切にしていること」「当面の重要な目標」をメッセージとして登録する機能。
- **複数のメッセージを登録・保持できる**(1件のみではなくリストとして管理する)。
- 権限: 初期バージョンはOwnerのみが追加・削除できる。
- 将来の権限委譲方針はチャットルームURL機能と同様と推測されるが、明記された要件はない(7章参照)。

### 4.6 ガバナンストークン(ERC20)[要件漏れとして追加]

- 本プロジェクトの価値が上がった場合に将来DAO化を検討しており、その準備としてガバナンストークン(ERC20)を発行する。
- **DAOとしての機能(投票・提案等)は今回実装しない**。トークンの発行のみを行う。
- 通常のERC20機能に加え、「このプロジェクト公式のトークンである」ことを示すため、`CommunityBoard`に当該ERC20のコントラクトアドレスを`public`変数として保持し、デプロイ後は変更不可(immutable)とする。
- 発行時にOwnerへ100,000,000,000単位をミントする。この数値が「トークンの個数(小数点を考慮しない人間可読の単位)」を指すのか、「ERC20の最小単位(`decimals`を考慮した生の値)」を指すのか、要確認(8章のOpen Questionとする)。
- トークン名・シンボルは未確定(8章のOpen Questionとする)。

## 5. 権限モデル(初期バージョン)

| ロール | 権限 |
|---|---|
| Owner(デプロイ者、初期メンバー#1を兼ねる) | チャットルームURLの追加・削除、理念/目標メッセージの追加・削除、任意メンバーの削除。ガバナンストークン発行時の全量ミント先 |
| メンバー | 新規メンバーの追加(単独で実行可能、他メンバーの承認・合議は不要)、自分自身の削除(脱退) |
| 誰でも(非メンバー含む) | オンチェーンデータの閲覧(ブロックチェーンの性質上、公開データは誰でも閲覧可能)。ガバナンストークンの保有・譲渡は誰でも可能(標準ERC20) |

将来的にはOwnerの権限を、メンバー投票で選出されたCouncilが管理するマルチシグ等のアドレスへ `Ownable.transferOwnership()` で委譲する想定(アップグレード可能コントラクトは採用しない。7.3参照)。

## 6. 非機能要件

- チェーン非依存: コントラクトはEthereum系(EVM)とPolkadot Hub系のどちらにもデプロイできる実装とすること(本番運用は3.3の方針により1チェーンのみ)。
- 個人情報を保持しないこと(2.2/4.2)。
- 承認者の記録など、ガバナンス上重要な操作の履歴はオンチェーンで検証可能であること。
- アップグレード不可能(非プロキシ)なコントラクトであること([ADR-0004](../adr/0004-ownable-governance-model.md))。

## 7. 矛盾・重大な課題として指摘した事項と決定内容

要件定義時に**論理的な矛盾・欠落・重大なリスク**として指摘した事項と、それぞれの決定内容を記録する。

### 7.1 [解決済み] 最初のメンバーが存在しない(ブートストラップ問題)

「メンバーになるには既存メンバーの承認が必要」というルールをそのまま適用すると、コントラクトデプロイ直後は既存メンバーが1人もいないため、誰も最初のメンバーになれない。

**決定**: デプロイ時にOwnerを「メンバー#1」として自動登録する(4.1に反映)。

### 7.2 [解決済み] マルチチェーンにおけるメンバーシップの整合性

Ethereum系とPolkadot Hub系それぞれに独立したコントラクトをデプロイする場合、メンバーシップの状態はチェーンごとに別々に管理され、自動的には同期されない。

**決定**: 本番運用(Mainnet)ではEthereum / Polkadot Hubのどちらか一方のみを選び、単一チェーンで運用する。両チェーンを同時に本番運用することはしないため、メンバーシップの不整合は発生しない(3.3に反映)。テストネットでは開発・検証のため両方を使用する。

### 7.3 [解決済み] Owner権限の将来のCouncilへの委譲方法

**決定**: `Ownable.transferOwnership()` による権限移譲で対応する。アップグレード可能コントラクト(プロキシパターン)は採用しない。Council選挙ロジック自体は将来フェーズのスコープであり、初期バージョンでは実装しない(5章に反映)。

### 7.4 [受容済みリスク] Sybil耐性の欠如

**決定**: 対策不要と判断。本プロジェクトは、オンラインで匿名に集める設計ではなく、オフラインも含め実際に面識があり信頼できる人物のみを既存メンバーが判断して招待・承認する運用を前提とする。この人的な信頼関係がSybil耐性の代替となるため、追加のオンチェーン対策は行わない。

### 7.5 [受容済みリスク] 疑似匿名性であり匿名性ではない

**決定**: 本プロジェクトの活動は合法な範囲での政策提言・世論形成を想定しており、違法行為を前提としない。そのため匿名性に関する追加対策(利用規約上の注意喚起以上のもの)は不要と判断する。

### 7.6 [解決済み] メンバーの削除・脱退

**決定**: メンバーの削除権限は、本人(自己脱退)とOwnerのみが持つ。メンバー同士による相互削除はできない(4.1・5章に反映)。

### 7.7 [解決済み] ステーブルコイン対応の意味

**決定**: 無視してよい。初期バージョンでは考慮不要であり、将来の拡張余地を残すための設計上の配慮も不要と判断した(4.3に反映)。将来ステーブルコイン対応が必要になった際は、改めて要件定義から行う。

### 7.8 [解決済み] Polkadot HubへのFoundryデプロイの成熟度

Polkadot Hubの公式ドキュメントを調査した結果、Solidity実行バックエンドには以下の2種類があることを確認した。

| バックエンド | 実行方式 | Foundry対応 | 成熟度 |
|---|---|---|---|
| REVM | 標準EVMバイトコードをRust実装で実行 | 素のFoundry/Hardhatがそのまま利用可(`--chain polkadot` / `--chain polkadot-testnet`) | 安定(不安定性に関する注記なし) |
| PolkaVM(PVM) | RISC-V独自VM、`resolc`コンパイラが必要 | 専用フォーク(foundry-polkadot)や`--resolc`フラグ等、専用対応が必要 | 公式ドキュメントに "early-stage development and may be unstable or incomplete" と明記 |

**決定**: REVM実行バックエンド + 素のFoundryを採用する。PolkaVM/`resolc`はユーザーのソフトウェア選定方針(安定版のみ採用)に反するため、現時点では採用しない。詳細は [ADR-0003](../adr/0003-use-foundry-with-revm-backend-for-polkadot-hub.md) を参照。

Sources: [Use Foundry with Polkadot Hub](https://docs.polkadot.com/smart-contracts/dev-environments/foundry/) / [Polkadot Hub Smart Contracts](https://docs.polkadot.com/reference/polkadot-hub/smart-contracts/)

## 8. その他の確認事項への回答

- [x] ステーブルコイン対応の具体的な意味 → 無視してよい(7.7)。
- [x] 本番運用(Mainnet)でEthereumとPolkadot Hubのどちらを選ぶか → 要件定義のスコープ外。デプロイ時に運用判断として決定する(3.3)。
- [x] メンバー追加に必要な人数 → 既存メンバー1名が単独で追加可能。他メンバーの承認は不要(4.1・5章)。
- [x] チャットルームURL・理念メッセージは1件のみ保持か、複数保持か → 複数保持する(4.4・4.5)。
- [x] Polkadot Hub Testnet/Mainnetの正式名称・RPCエンドポイント・Chain ID → docs.polkadot.comで確認済み。Testnet: Chain ID `420420417`・通貨`PAS`。Mainnet: Chain ID `420420419`・通貨`DOT`。詳細は[ADR-0003](../adr/0003-use-foundry-with-revm-backend-for-polkadot-hub.md)・[003-software-versions.md](../design/003-software-versions.md)参照。

- [ ] **ガバナンストークンの名称・シンボル**(4.6): 未確定。実装前に確認する。
- [ ] **ミント数量「100,000,000,000」の単位**(4.6): 人間可読のトークン枚数(例: `100_000_000_000 * 10^18`を`_mint`する)か、ERC20の生の最小単位(`decimals`込みでそのまま`100000000000`を`_mint`する。実質0.0000001枚相当)か未確定。[ADR-0006](../adr/0006-governance-token.md)では前者(人間可読のトークン枚数)と解釈して提案しているが、実装前に確認する。
- [ ] **ガバナンストークンにミント権限を残すか**(将来のDAO化に備えて追加ミットを可能にするか、それとも初回ミントのみで供給量を完全に固定するか)。[ADR-0006](../adr/0006-governance-token.md)では固定供給(追加ミント不可)を提案しているが、実装前に確認する。

上記3点は実装着手前に確認が必要。それ以外に実装をブロックするOpen Questionはない。
