## 1. 目的

初期バージョン(MVP)の実装が「完了した」と判断するための客観的な基準を定義する。ここに定義した基準を満たすまでは完了として扱わない。

## 2. 完了条件

### 2.1 機能実装

- [ ] [コントラクト基本設計書](../design/001-contract-design.md)に記載された`Membership.sol`・`CommunityBoard.sol`の全関数が実装されている
- [ ] [フロントエンド基本設計書](../design/002-frontend-design.md)に記載された全画面・全コンポーネントが実装されている

### 2.2 コントラクトのテスト

- [ ] Foundryでテストコードを実装し、`forge test`が全件成功する
- [ ] `forge coverage`のカバレッジが **line / statement / branch / function すべて100%**
  - 100%達成が現実的に困難な箇所(例: Solidityコンパイラが自動生成する到達不能コード等)がある場合は、この文書に理由と該当箇所を明記した上で除外する。理由を示さない未達は認めない。

### 2.3 フロントエンドのテスト

「行カバレッジ100%」は採用しない(理由は3章)。代わりに以下の3つを完了基準とする。

- [ ] **ユニット/コンポーネントテスト**: `lib/`配下の純粋ロジック・カスタムフックのライン/ブランチカバレッジ80%以上(Vitest + Testing Library)
- [ ] **E2Eゴールデンパス**: 4章に列挙する全シナリオが、Playwrightのテストとして実装され成功する(100%)
- [ ] **権限状態カバレッジ**: 「訪問者」「メンバー」「Owner」の3ロールそれぞれについて、表示されるUIが要件通りであることを確認するテストが存在する

### 2.4 全体

- [ ] コントラクト・フロントエンド双方のテストがCI上で green であること
- [ ] Lint・型チェック(TypeScript / Solidity)がエラーなしであること

## 3. なぜフロントエンドは「行カバレッジ100%」にしないのか

コントラクトと異なり、フロントエンドの行カバレッジ100%は次の理由で有効な指標にならないと考える。

- wagmiのフック(`useReadContract`/`useWriteContract`等)はローディング・エラー・成功など多数の内部分岐を持ち、その全パスを網羅しても実際の不具合検出にはほとんど寄与しない(ライブラリ側の責務であり、アプリ側でテストすべき対象ではない)。
- 行カバレッジは「そのコードが実行されたか」しか示さず、「ウォレット接続時にメンバー以外へ追加ボタンが表示されない」といった**要件との整合性**は保証しない。
- 100%を機械的に追い求めると、価値の低いテスト(実装の詳細をなぞるだけのテスト)を書くインセンティブが生まれる。

そのため、[要件定義4.1〜4.5](./001-mvp-requirements.md)に対応する実際のユーザー操作シナリオ(4章のゴールデンパス)を100%カバーすることを主指標とし、コードの機械的な網羅率(ユニットテストの80%)は補助指標として扱う。

## 4. ゴールデンパス一覧(E2Eテスト対象)

1. 未接続の訪問者がホーム画面を閲覧できる(Mission Log / Comms Channels / Party Roster、いずれも読み取り専用)
2. ウォレットを接続すると、自分のアドレスと接続中のネットワークが表示される
3. 既存メンバーが、他メンバーの承認を必要とせず単独で新規メンバーを追加できる
4. メンバーが自分自身を脱退(セルフ削除)できる
5. 非メンバー・非Ownerには、追加・削除系の操作UI(Add Member、チャットルーム/メッセージの編集ボタン等)が表示されない
6. Ownerがチャットルームを追加・削除できる
7. Ownerが理念・目標メッセージを追加・削除できる
8. コントラクト未対応のネットワークに接続している場合、適切な警告が表示され誤操作を防ぐ
